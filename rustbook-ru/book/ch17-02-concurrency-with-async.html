Язык программирования Rust

Применение конкурентности с async

В этом разделе мы применим async к некоторым из тех же задач конкурентного выполнения, которые решали с помощью потоков в главе 16. Поскольку многие ключевые идеи мы уже обсуждали там, здесь сосредоточимся на различиях между потоками и фьючерсами.

Во многих случаях API для работы с конкурентностью посредством async очень похожи на API для работы с потоками. В других случаях они оказываются совершенно разными. Даже когда API потоков и async выглядят похоже, их поведение часто различается, а характеристики производительности почти всегда отличаются.

Создание новой задачи с помощью spawn_task

Первой операцией, которую мы рассмотрели в разделе «Создание нового потока с помощью spawn» главы 16, был подсчёт чисел в двух отдельных потоках. Давайте сделаем то же самое с помощью async. Крейт trpl предоставляет функцию spawn_task, очень похожую на API thread::spawn, и функцию sleep — асинхронную версию API thread::sleep. Используя их вместе, мы можем реализовать пример с подсчётом, как показано в Листинге 17-6.

extern crate trpl; // required for mdbook test

use std::time::Duration;

fn main() {
    trpl::block_on(async {
        trpl::spawn_task(async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        });

        for i in 1..5 {
            println!("hi number {i} from the second task!");
            trpl::sleep(Duration::from_millis(500)).await;
        }
    });
}

В качестве отправной точки мы настраиваем функцию main с помощью trpl::block_on, чтобы наша функция верхнего уровня могла быть асинхронной.

Примечание: Начиная с этого места и до конца главы каждый пример будет содержать точно такую же обёртку с trpl::block_on в main. Поэтому мы часто будем опускать её, как и саму main. Не забывайте добавлять её в свой код!

Затем внутри этого блока мы записываем два цикла. Каждый из них содержит вызов trpl::sleep, который ожидает полсекунды (500 миллисекунд) перед отправкой следующего сообщения. Один цикл помещаем в тело trpl::spawn_task, а другой оставляем в цикле for верхнего уровня. После вызовов sleep мы также добавляем await.

Этот код ведёт себя примерно так же, как реализация на потоках, — в том числе сообщения в вашем терминале при запуске могут появляться в другом порядке:

hi number 1 from the second task!
hi number 1 from the first task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!

Эта версия останавливается сразу после завершения цикла for в теле главного асинхронного блока, поскольку задача, созданная с помощью spawn_task, завершается при окончании функции main. Если вы хотите, чтобы она выполнялась до полного завершения задачи, потребуется использовать дескриптор объединения (join handle), чтобы дождаться окончания первой задачи. Для потоков мы использовали метод join, который «блокировал» выполнение до тех пор, пока поток не завершался. В Листинге 17-7 мы можем сделать то же самое с помощью await, поскольку сам дескриптор задачи является фьючерсом. Его тип Output — Result, поэтому после ожидания мы также распаковываем результат.

extern crate trpl; // required for mdbook test

use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let handle = trpl::spawn_task(async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        });

        for i in 1..5 {
            println!("hi number {i} from the second task!");
            trpl::sleep(Duration::from_millis(500)).await;
        }

        handle.await.unwrap();
    });
}

Эта обновлённая версия работает до тех пор, пока не завершатся оба цикла:

hi number 1 from the second task!
hi number 1 from the first task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
hi number 6 from the first task!
hi number 7 from the first task!
hi number 8 from the first task!
hi number 9 from the first task!

Пока кажется, что async и потоки дают похожие результаты, отличаясь лишь синтаксисом: вместо вызова join у дескриптора объединения мы используем await, а также ожидаем завершения вызовов sleep.

Главное отличие состоит в том, что нам не пришлось создавать для этого ещё один поток операционной системы. Более того, нам даже не обязательно создавать отдельную задачу. Поскольку асинхронные блоки компилируются в анонимные фьючерсы, мы можем поместить каждый цикл в асинхронный блок и поручить среде выполнения выполнить оба блока до конца с помощью функции trpl::join.

В разделе «Ожидание завершения всех потоков» главы 16 мы показали, как использовать метод join типа JoinHandle, возвращаемого при вызове std::thread::spawn. Функция trpl::join похожа на него, но предназначена для фьючерсов. Если передать ей два фьючерса, она создаст один новый фьючерс, результатом которого будет кортеж с результатами каждого из переданных фьючерсов после того, как оба завершатся. Поэтому в Листинге 17-8 мы используем trpl::join, чтобы дождаться завершения fut1 и fut2. Мы не ожидаем fut1 и fut2 по отдельности, а ожидаем новый фьючерс, созданный trpl::join. Результат нам не нужен, поскольку это всего лишь кортеж из двух значений типа unit.

extern crate trpl; // required for mdbook test

use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let fut1 = async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let fut2 = async {
            for i in 1..5 {
                println!("hi number {i} from the second task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        trpl::join(fut1, fut2).await;
    });
}

При запуске мы увидим, что оба фьючерса выполняются до завершения:

hi number 1 from the first task!
hi number 1 from the second task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
hi number 6 from the first task!
hi number 7 from the first task!
hi number 8 from the first task!
hi number 9 from the first task!

Теперь вы будете видеть один и тот же порядок при каждом запуске. Это сильно отличается от того, что мы наблюдали с потоками и trpl::spawn_task в Листинге 17-7. Причина в том, что функция trpl::join является справедливой: она одинаково часто проверяет каждый фьючерс, чередуя их, и не позволяет одному фьючерсу убежать вперёд, если другой готов к выполнению. При работе с потоками операционная система решает, какой поток проверять и как долго позволять ему работать. В асинхронном Rust это решает среда выполнения. (На практике всё несколько сложнее, поскольку асинхронная среда выполнения может использовать потоки операционной системы внутри себя для управления конкурентностью, поэтому обеспечение справедливости может потребовать от неё дополнительных усилий. Но это всё равно возможно!) Среды выполнения не обязаны гарантировать справедливость для каждой операции и часто предлагают разные API, позволяющие выбрать, нужна ли она вам.

Попробуйте некоторые из следующих вариантов ожидания фьючерсов и посмотрите, что произойдёт:

  • Удалите асинхронный блок вокруг одного или обоих циклов.
  • Ожидайте каждый асинхронный блок сразу после его определения.
  • Оберните в асинхронный блок только первый цикл, а полученный фьючерс ожидайте после тела второго цикла.

В качестве дополнительного испытания попробуйте определить, каким будет вывод в каждом случае, до запуска программы!

Передача данных между двумя задачами с помощью обмена сообщениями

Совместное использование данных между фьючерсами тоже покажется знакомым: мы снова воспользуемся передачей сообщений, но на этот раз асинхронными версиями типов и функций. Мы пойдём немного другим путём, чем в разделе «Передача данных между потоками с помощью обмена сообщениями» главы 16, чтобы показать некоторые ключевые различия между конкурентностью на основе потоков и на основе фьючерсов. В Листинге 17-9 мы начнём всего с одного асинхронного блока, не создавая отдельную задачу, как мы ранее создавали отдельный поток.

extern crate trpl; // required for mdbook test

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let val = String::from("hi");
        tx.send(val).unwrap();

        let received = rx.recv().await.unwrap();
        println!("received '{received}'");
    });
}

Здесь мы используем trpl::channel — асинхронную версию API канала с несколькими отправителями и одним получателем, который мы использовали с потоками в главе 16. Асинхронная версия API лишь немного отличается от версии для потоков: она использует изменяемый получатель rx вместо неизменяемого, а её метод recv создаёт фьючерс, которого нам нужно дождаться, вместо того чтобы сразу возвращать значение. Теперь мы можем отправлять сообщения от отправителя получателю. Обратите внимание: нам не нужно создавать отдельный поток или даже задачу — достаточно дождаться вызова rx.recv.

Синхронный метод Receiver::recv из std::mpsc::channel блокирует выполнение до получения сообщения. Метод trpl::Receiver::recv этого не делает, поскольку он асинхронный. Вместо блокировки он возвращает управление среде выполнения до тех пор, пока не будет получено сообщение или пока отправляющая сторона канала не закроется. Напротив, вызов send мы не ожидаем, поскольку он не блокирует выполнение. В этом нет необходимости, потому что канал, в который мы отправляем сообщения, не имеет ограничения на размер очереди.

Примечание: Поскольку весь этот асинхронный код выполняется внутри асинхронного блока в вызове trpl::block_on, всё внутри него может обходиться без блокировки. Однако код вне этого блока будет заблокирован до возврата функции block_on. В этом и заключается назначение trpl::block_on: она позволяет вам выбрать, где блокировать выполнение при запуске некоторого асинхронного кода, а значит, определить место перехода между синхронным и асинхронным кодом.

В этом примере стоит обратить внимание на две вещи. Во-первых, сообщение поступит немедленно. Во-вторых, хотя здесь мы используем фьючерс, конкурентности пока нет. Всё в листинге происходит последовательно, точно так же, как если бы фьючерсы вообще не использовались.

Решим первую проблему, отправляя последовательность сообщений и делая паузу между ними, как показано в Листинге 17-10.

extern crate trpl; // required for mdbook test

use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let vals = vec![
            String::from("hi"),
            String::from("from"),
            String::from("the"),
            String::from("future"),
        ];

        for val in vals {
            tx.send(val).unwrap();
            trpl::sleep(Duration::from_millis(500)).await;
        }

        while let Some(value) = rx.recv().await {
            println!("received '{value}'");
        }
    });
}

Помимо отправки сообщений, нам нужно их получать. В данном случае, поскольку мы знаем, сколько сообщений придёт, мы могли бы сделать это вручную, вызвав rx.recv().await четыре раза. Однако в реальном мире нам обычно приходится ожидать неизвестное количество сообщений, поэтому нужно продолжать ожидание, пока мы не определим, что сообщений больше нет.

В Листинге 16-10 мы использовали цикл for для обработки всех элементов, полученных из синхронного канала. Однако в Rust пока нет способа использовать цикл for с асинхронно создаваемой последовательностью элементов. Поэтому нам нужно воспользоваться циклом, который мы ещё не рассматривали: условным циклом while let. Это циклический вариант конструкции if let, которую мы изучали в разделе «Краткое управление потоком с помощью if let и let…else» главы 6. Цикл продолжает выполняться, пока заданный шаблон сопоставляется со значением.

Вызов rx.recv создаёт фьючерс, которого мы ожидаем. Среда выполнения приостановит этот фьючерс, пока он не будет готов. Когда приходит сообщение, фьючерс разрешается в Some(message) — так происходит для каждого полученного сообщения. Когда канал закрывается, независимо от того, пришли ли вообще какие-нибудь сообщения, фьючерс разрешается в None, указывая, что значений больше не будет и, следовательно, опрос нужно прекратить, то есть больше не нужно ожидать его завершения.

Цикл while let объединяет всё это. Если результат вызова rx.recv().await — Some(message), мы получаем доступ к сообщению и можем использовать его в теле цикла, как и в случае с if let. Если результат — None, цикл завершается. Каждый раз после завершения тела цикла выполнение снова доходит до точки ожидания, поэтому среда выполнения снова приостанавливает его до поступления следующего сообщения.

Теперь код успешно отправляет и получает все сообщения. К сожалению, остаётся ещё пара проблем. Во-первых, сообщения приходят не с интервалом в полсекунды. Вместо этого все они поступают одновременно, через 2 секунды (2000 миллисекунд) после запуска программы. Во-вторых, программа никогда не завершается! Вместо этого она бесконечно ждёт новые сообщения. Чтобы остановить её, придётся нажать ctrl-C.

Код внутри одного асинхронного блока выполняется последовательно

Начнём с выяснения, почему все сообщения приходят одновременно после полной задержки, а не с паузами между ними. Внутри заданного асинхронного блока порядок появления ключевых слов await в коде совпадает с порядком их выполнения при запуске программы.

В Листинге 17-10 есть только один асинхронный блок, поэтому всё внутри него выполняется последовательно. Конкурентности по-прежнему нет. Все вызовы tx.send происходят вперемешку с вызовами trpl::sleep и соответствующими точками ожидания. И только после этого цикл while let доходит до точек ожидания в вызовах recv.

Чтобы получить желаемое поведение, при котором между отправками сообщений выдерживается пауза, нужно поместить операции tx и rx в собственные асинхронные блоки, как показано в Листинге 17-11. Тогда среда выполнения сможет выполнять их отдельно друг от друга с помощью trpl::join, как в Листинге 17-8. И снова мы ожидаем результат вызова trpl::join, а не отдельные фьючерсы. Если бы мы ожидали отдельные фьючерсы последовательно, то вернулись бы к последовательному выполнению — именно от него мы и пытаемся уйти.

extern crate trpl; // required for mdbook test

use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let tx_fut = async {
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        trpl::join(tx_fut, rx_fut).await;
    });
}

В обновлённом коде из Листинга 17-11 сообщения выводятся с интервалом в 500 миллисекунд, а не все разом через 2 секунды.

Перемещение владения внутрь асинхронного блока

Однако программа всё ещё никогда не завершается из-за того, как цикл while let взаимодействует с trpl::join:

  • Фьючерс, возвращаемый trpl::join, завершается только после того, как завершатся оба переданных ему фьючерса.
  • Фьючерс tx_fut завершается, когда заканчивается ожидание после отправки последнего сообщения из vals.
  • Фьючерс rx_fut не завершится, пока не закончится цикл while let.
  • Цикл while let не завершится, пока ожидание rx.recv не вернёт None.
  • Ожидание rx.recv вернёт None только после закрытия другого конца канала.
  • Канал закроется только в том случае, если мы вызовем rx.close или будет удалён отправитель tx.
  • Мы нигде не вызываем rx.close, а tx не будет удалён, пока не завершится внешний асинхронный блок, переданный в trpl::block_on.
  • Блок не может завершиться, потому что он заблокирован ожиданием завершения trpl::join, что возвращает нас к началу этого списка.

Сейчас асинхронный блок, в котором мы отправляем сообщения, только заимствует tx, поскольку для отправки сообщения владение не требуется. Но если бы мы могли переместить tx в этот асинхронный блок, то после завершения блока он был бы удалён. В разделе «Захват ссылок или перемещение владения» главы 13 вы узнали, как использовать ключевое слово move с замыканиями. А в разделе «Использование замыканий move с потоками» главы 16 мы обсуждали, что при работе с потоками часто приходится перемещать данные в замыкания. Та же основная логика применима к асинхронным блокам, поэтому ключевое слово move работает с ними так же, как с замыканиями.

В Листинге 17-12 мы меняем блок, используемый для отправки сообщений, с async на async move.

extern crate trpl; // required for mdbook test

use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let tx_fut = async move {
            // --snip--
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        trpl::join(tx_fut, rx_fut).await;
    });
}

При запуске этой версии программа корректно завершается после отправки и получения последнего сообщения. Теперь посмотрим, что нужно изменить, чтобы отправлять данные более чем из одного фьючерса.

Объединение нескольких фьючерсов с помощью макроса join!

Этот асинхронный канал также поддерживает несколько отправителей, поэтому мы можем вызвать clone для tx, если хотим отправлять сообщения из нескольких фьючерсов, как показано в Листинге 17-13.

extern crate trpl; // required for mdbook test

use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let tx1 = tx.clone();
        let tx1_fut = async move {
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx1.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        let tx_fut = async move {
            let vals = vec![
                String::from("more"),
                String::from("messages"),
                String::from("for"),
                String::from("you"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(1500)).await;
            }
        };

        trpl::join!(tx1_fut, tx_fut, rx_fut);
    });
}

Сначала мы клонируем tx, создавая tx1 вне первого асинхронного блока. Затем перемещаем tx1 в этот блок, как ранее поступили с tx. Позже мы перемещаем исходный tx в новый асинхронный блок, где отправляем дополнительные сообщения с немного большей задержкой. Мы расположили этот новый асинхронный блок после блока для получения сообщений, но его можно было бы расположить и перед ним. Главное — порядок, в котором ожидаются фьючерсы, а не порядок их создания.

Оба асинхронных блока для отправки сообщений должны быть блоками async move, чтобы tx и tx1 удалялись после завершения этих блоков. В противном случае мы снова окажемся в бесконечном цикле, с которого начинали.

Наконец, мы заменяем trpl::join на trpl::join!, чтобы обработать дополнительный фьючерс. Макрос join! ожидает произвольное количество фьючерсов, если их количество известно во время компиляции. Позже в этой главе мы обсудим, как ожидать коллекцию фьючерсов, количество которых заранее неизвестно.

Теперь мы видим все сообщения от обоих фьючерсов-отправителей. Поскольку после отправки сообщения они используют немного разные задержки, сообщения также принимаются через разные интервалы:
