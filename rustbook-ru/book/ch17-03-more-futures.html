Передача управления среде выполнения

Вспомните раздел «Наша первая асинхронная программа»: в каждой точке ожидания Rust предоставляет среде выполнения возможность приостановить задачу и переключиться на другую, если ожидаемый фьючерс ещё не готов. Верно и обратное: Rust приостанавливает асинхронные блоки и возвращает управление среде выполнения только в точках ожидания. Всё, что находится между точками ожидания, выполняется синхронно.

Это означает, что если внутри асинхронного блока выполнить много работы без единой точки ожидания, такой фьючерс не позволит другим фьючерсам продвигаться вперёд. Иногда это называют тем, что один фьючерс лишает другие фьючерсы ресурсов (starving). В некоторых случаях это не представляет большой проблемы. Однако если вы выполняете ресурсоёмкую подготовительную работу, длительную операцию или у вас есть фьючерс, который бесконечно выполняет определённую задачу, необходимо продумать, когда и где возвращать управление среде выполнения.

Давайте смоделируем длительную операцию, чтобы показать проблему голодания, а затем рассмотрим способы её решения. В Листинге 17-14 представлена функция slow.

extern crate trpl; // required for mdbook test

use std::{thread, time::Duration};

fn main() {
    trpl::block_on(async {
        // We will call `slow` here later
    });
}

fn slow(name: &str, ms: u64) {
    thread::sleep(Duration::from_millis(ms));
    println!("'{name}' ran for {ms}ms");
}

В этом коде используется std::thread::sleep, а не trpl::sleep, поэтому вызов slow блокирует текущий поток на заданное количество миллисекунд. С помощью slow мы можем имитировать реальные операции, которые одновременно являются длительными и блокирующими.

В Листинге 17-15 мы используем slow, чтобы имитировать выполнение такой работы, ограниченной производительностью процессора, в паре фьючерсов.

extern crate trpl; // required for mdbook test

use std::{thread, time::Duration};

fn main() {
    trpl::block_on(async {
        let a = async {
            println!("'a' started.");
            slow("a", 30);
            slow("a", 10);
            slow("a", 20);
            trpl::sleep(Duration::from_millis(50)).await;
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            slow("b", 10);
            slow("b", 15);
            slow("b", 350);
            trpl::sleep(Duration::from_millis(50)).await;
            println!("'b' finished.");
        };

        trpl::select(a, b).await;
    });
}

fn slow(name: &str, ms: u64) {
    thread::sleep(Duration::from_millis(ms));
    println!("'{name}' ran for {ms}ms");
}

Каждый фьючерс возвращает управление среде выполнения только после выполнения нескольких медленных операций. Если запустить этот код, вы увидите следующий вывод:

'a' started.
'a' ran for 30ms
'a' ran for 10ms
'a' ran for 20ms
'b' started.
'b' ran for 75ms
'b' ran for 10ms
'b' ran for 15ms
'b' ran for 350ms
'a' finished.

Как и в Листинге 17-5, где мы использовали trpl::select для гонки фьючерсов, загружающих два URL-адреса, select по-прежнему завершается сразу после окончания a. Однако вызовы slow в двух фьючерсах не чередуются. Фьючерс a выполняет всю свою работу до тех пор, пока не доходит до ожидания вызова trpl::sleep. Затем всю свою работу выполняет фьючерс b, пока не доходит до собственного вызова trpl::sleep, и, наконец, завершается фьючерс a. Чтобы оба фьючерса могли продвигаться вперёд между медленными операциями, нам нужны точки ожидания, в которых мы сможем вернуть управление среде выполнения. Значит, нам нужно что-то, чего можно дождаться!

Мы уже можем увидеть такую передачу управления в Листинге 17-15: если удалить trpl::sleep в конце фьючерса a, он завершится, так и не позволив фьючерсу b вообще запуститься. Давайте попробуем использовать функцию trpl::sleep как отправную точку, чтобы операции могли поочерёдно получать возможность продвигаться вперёд, как показано в Листинге 17-16.

extern crate trpl; // required for mdbook test

use std::{thread, time::Duration};

fn main() {
    trpl::block_on(async {
        let one_ms = Duration::from_millis(1);

        let a = async {
            println!("'a' started.");
            slow("a", 30);
            trpl::sleep(one_ms).await;
            slow("a", 10);
            trpl::sleep(one_ms).await;
            slow("a", 20);
            trpl::sleep(one_ms).await;
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            trpl::sleep(one_ms).await;
            slow("b", 10);
            trpl::sleep(one_ms).await;
            slow("b", 15);
            trpl::sleep(one_ms).await;
            slow("b", 350);
            trpl::sleep(one_ms).await;
            println!("'b' finished.");
        };

        trpl::select(a, b).await;
    });
}

fn slow(name: &str, ms: u64) {
    thread::sleep(Duration::from_millis(ms));
    println!("'{name}' ran for {ms}ms");
}

Мы добавили вызовы trpl::sleep с точками ожидания между каждым вызовом slow. Теперь работа двух фьючерсов чередуется:

'a' started.
'a' ran for 30ms
'b' started.
'b' ran for 75ms
'a' ran for 10ms
'b' ran for 10ms
'a' ran for 20ms
'b' ran for 15ms
'a' finished.

Фьючерс a всё ещё выполняется некоторое время, прежде чем передать управление b, поскольку он вызывает slow до первого вызова trpl::sleep. Но после этого фьючерсы переключаются туда и обратно каждый раз, когда один из них достигает точки ожидания. В данном случае мы делаем это после каждого вызова slow, но можем разделить работу любым способом, который лучше подходит для нашей задачи.

Однако на самом деле мы не хотим здесь спать: мы хотим продвигаться вперёд настолько быстро, насколько это возможно. Нам нужно лишь вернуть управление среде выполнения. Это можно сделать напрямую с помощью функции trpl::yield_now. В Листинге 17-17 мы заменяем все вызовы trpl::sleep на trpl::yield_now.

extern crate trpl; // required for mdbook test

use std::{thread, time::Duration};

fn main() {
    trpl::block_on(async {
        let a = async {
            println!("'a' started.");
            slow("a", 30);
            trpl::yield_now().await;
            slow("a", 10);
            trpl::yield_now().await;
            slow("a", 20);
            trpl::yield_now().await;
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            trpl::yield_now().await;
            slow("b", 10);
            trpl::yield_now().await;
            slow("b", 15);
            trpl::yield_now().await;
            slow("b", 350);
            trpl::yield_now().await;
            println!("'b' finished.");
        };

        trpl::select(a, b).await;
    });
}

fn slow(name: &str, ms: u64) {
    thread::sleep(Duration::from_millis(ms));
    println!("'{name}' ran for {ms}ms");
}

Этот код яснее выражает фактическое намерение и может работать значительно быстрее, чем вариант с sleep, поскольку таймеры, подобные используемому в sleep, часто имеют ограничения на точность. Например, используемая нами версия sleep всегда будет ожидать не менее одной миллисекунды, даже если передать ей Duration длительностью в одну наносекунду. И снова напомним: современные компьютеры быстрые — за одну миллисекунду они способны выполнить очень много операций!

Это означает, что async может быть полезен даже для задач, ограниченных производительностью процессора, в зависимости от того, что ещё делает программа: он предоставляет удобный инструмент для организации взаимодействия между разными частями программы (хотя и с накладными расходами на машину состояний async). Это разновидность кооперативной многозадачности, при которой каждый фьючерс может самостоятельно определять, когда передать управление, используя точки ожидания. Следовательно, каждый фьючерс также несёт ответственность за то, чтобы не блокировать выполнение слишком долго. В некоторых встроенных операционных системах на основе Rust это единственный вид многозадачности!

В реальном коде вы, конечно, обычно не будете чередовать вызовы функций с точками ожидания в каждой строке. Хотя передача управления таким способом относительно недорога, она не бесплатна. Во многих случаях попытка разбить вычислительную задачу на части может значительно замедлить её выполнение, поэтому иногда для общей производительности лучше позволить операции ненадолго заблокировать выполнение. Всегда измеряйте производительность, чтобы определить реальные узкие места вашего кода. Тем не менее важно помнить об описанном механизме, если вы замечаете, что большая часть работы выполняется последовательно, хотя вы ожидали конкурентного выполнения!

Создание собственных асинхронных абстракций

Мы также можем объединять фьючерсы, создавая новые шаблоны взаимодействия. Например, мы можем создать функцию timeout из уже знакомых нам асинхронных строительных блоков. В результате мы получим ещё один строительный блок, который можно будет использовать для создания новых асинхронных абстракций.

В Листинге 17-18 показано, как, по нашим ожиданиям, должна работать функция timeout с медленным фьючерсом.

extern crate trpl; // required for mdbook test

use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let slow = async {
            trpl::sleep(Duration::from_secs(5)).await;
            "Finally finished"
        };

        match timeout(slow, Duration::from_secs(2)).await {
            Ok(message) => println!("Succeeded with '{message}'"),
            Err(duration) => {
                println!("Failed after {} seconds", duration.as_secs())
            }
        }
    });
}

Давайте реализуем эту функцию! Для начала подумаем об API timeout:

  • Сама функция должна быть асинхронной, чтобы мы могли ожидать её завершения.
  • Её первый параметр должен быть фьючерсом, который нужно выполнить. Мы можем сделать функцию обобщённой, чтобы она работала с любым фьючерсом.
  • Вторым параметром будет максимальное время ожидания. Если использовать Duration, его будет легко передать в trpl::sleep.
  • Функция должна возвращать Result. Если фьючерс успешно завершится, Result будет содержать Ok со значением, созданным фьючерсом. Если время ожидания истечёт раньше, Result будет содержать Err с длительностью, в течение которой функция ожидала.

В Листинге 17-19 показано объявление этой функции.

Теперь типы соответствуют нашим целям. Давайте подумаем о поведении, которое нам нужно реализовать: мы хотим устроить гонку между переданным фьючерсом и заданным интервалом времени. С помощью trpl::sleep можно создать фьючерс таймера из значения длительности, а затем использовать trpl::select, чтобы запустить этот таймер одновременно с фьючерсом, переданным вызывающей стороной.

В Листинге 17-20 мы реализуем timeout, сопоставляя результат ожидания trpl::select с помощью match.

extern crate trpl; // required for mdbook test

use std::time::Duration;

use trpl::Either;

// --snip--

fn main() {
    trpl::block_on(async {
        let slow = async {
            trpl::sleep(Duration::from_secs(5)).await;
            "Finally finished"
        };

        match timeout(slow, Duration::from_secs(2)).await {
            Ok(message) => println!("Succeeded with '{message}'"),
            Err(duration) => {
                println!("Failed after {} seconds", duration.as_secs())
            }
        }
    });
}

async fn timeout<F: Future>(
    future_to_try: F,
    max_time: Duration,
) -> Result<F::Output, Duration> {
    match trpl::select(future_to_try, trpl::sleep(max_time)).await {
        Either::Left(output) => Ok(output),
        Either::Right(_) => Err(max_time),
    }
}

Реализация trpl::select не является справедливой: она всегда опрашивает аргументы в том порядке, в котором они переданы (другие реализации select могут случайным образом выбирать, какой аргумент опрашивать первым). Поэтому мы передаём future_to_try в select первым, чтобы у него была возможность завершиться, даже если max_time имеет очень небольшую длительность. Если future_to_try завершится первым, select вернёт Left с результатом future_to_try. Если первым завершится timer, select вернёт Right с результатом таймера — ().

Если future_to_try успешно завершается и мы получаем Left(output), то возвращаем Ok(output). Если же срабатывает таймер ожидания и мы получаем Right(()), мы игнорируем () с помощью _ и вместо этого возвращаем Err(max_time).

Итак, у нас есть работающая функция timeout, построенная из двух других асинхронных вспомогательных функций. Если запустить код, после истечения времени ожидания он выведет сообщение о неудаче:

Failed after 2 seconds

Поскольку фьючерсы можно комбинировать с другими фьючерсами, из небольших асинхронных строительных блоков можно создавать очень мощные инструменты. Например, можно использовать тот же подход, чтобы объединить тайм-ауты с повторными попытками, а затем применять их к таким операциям, как сетевые запросы (например, в Листинге 17-5).

На практике вы обычно будете напрямую работать с async и await, а для управления выполнением внешних фьючерсов дополнительно использовать такие функции, как select, и макросы, например join!.

Мы рассмотрели несколько способов одновременной работы с несколькими фьючерсами. Далее мы узнаем, как работать с несколькими фьючерсами, последовательно поступающими с течением времени, используя потоки (streams).
