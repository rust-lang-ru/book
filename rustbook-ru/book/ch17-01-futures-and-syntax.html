Язык программирования Rust

Фьючерсы и синтаксис async

Ключевыми элементами асинхронного программирования в Rust являются фьючерсы и ключевые слова async и await.

Фьючерс — это значение, которое может быть не готово сейчас, но станет готовым в некоторый момент в будущем. (Та же концепция встречается во многих языках, иногда под другими названиями, например задача или обещание.) Rust предоставляет трейт Future в качестве строительного блока: благодаря ему различные асинхронные операции могут реализовываться с помощью разных структур данных, но иметь общий интерфейс. В Rust фьючерсами называются типы, реализующие трейт Future. Каждый фьючерс хранит собственную информацию о достигнутом прогрессе и о том, что означает состояние «готов».

К блокам и функциям можно применять ключевое слово async, указывая тем самым, что их выполнение можно приостанавливать и возобновлять. Внутри асинхронного блока или функции можно использовать ключевое слово await, чтобы дождаться фьючерса (то есть дождаться, пока он станет готов). Каждое место, в котором внутри асинхронного блока или функции ожидается фьючерс, является потенциальной точкой приостановки и последующего возобновления выполнения этого блока или функции. Процесс проверки фьючерса на предмет готовности его значения называется опросом (polling).

Некоторые другие языки, например C# и JavaScript, также используют ключевые слова async и await для асинхронного программирования. Если вы знакомы с этими языками, то можете заметить существенные различия в том, как Rust обрабатывает этот синтаксис. И на то есть веская причина, которую мы скоро увидим!

При написании асинхронного кода на Rust мы большую часть времени используем ключевые слова async и await. Rust компилирует их в эквивалентный код, использующий трейт Future, примерно так же, как он компилирует циклы for в эквивалентный код с использованием трейта Iterator. Однако, поскольку Rust предоставляет трейт Future, вы также можете реализовать его для собственных типов данных, когда это необходимо. Многие функции, которые мы рассмотрим в этой главе, возвращают типы с собственной реализацией Future. В конце главы мы вернёмся к определению этого трейта и подробнее разберём его работу. Пока же этих сведений достаточно, чтобы двигаться дальше.

Всё это может показаться несколько абстрактным, поэтому давайте напишем нашу первую асинхронную программу — небольшой веб-скрейпер. Мы передадим ему из командной строки два URL-адреса, запросим обе страницы конкурентно и вернём результат той из них, обработка которой завершится первой. В этом примере будет довольно много нового синтаксиса, но не беспокойтесь: по ходу дела мы объясним всё необходимое.

Наша первая асинхронная программа

Чтобы сосредоточиться в этой главе на изучении async, а не на работе с различными частями экосистемы, мы создали крейт trpl (trpl — сокращение от “The Rust Programming Language”). Он повторно экспортирует все необходимые вам типы, трейты и функции, преимущественно из крейтов futures и tokio. Крейтом futures пользуются как официальной площадкой для экспериментов с асинхронным кодом в Rust; именно там изначально был разработан трейт Future. Tokio сегодня является наиболее широко используемой средой выполнения асинхронного кода в Rust, особенно в веб-приложениях. Существуют и другие отличные среды выполнения, которые могут лучше подойти для ваших задач. Крейт tokio используется внутри trpl, поскольку он хорошо протестирован и широко распространён.

В некоторых случаях trpl также переименовывает исходные API или оборачивает их, чтобы сосредоточить ваше внимание на деталях, важных для этой главы. Если вы хотите понять, что именно делает этот крейт, рекомендуем изучить его исходный код. Вы сможете увидеть, из какого крейта происходит каждый повторно экспортируемый элемент; кроме того, мы оставили подробные комментарии, объясняющие назначение кода.

Создайте новый бинарный проект с именем hello-async и добавьте крейт trpl в качестве зависимости:

$ cargo new hello-async
$ cd hello-async
$ cargo add trpl

Теперь мы можем использовать различные элементы, предоставляемые trpl, чтобы написать нашу первую асинхронную программу. Мы создадим небольшую утилиту командной строки, которая загружает две веб-страницы, извлекает из каждой элемент <title> и выводит заголовок той страницы, обработка которой завершится первой.

Определение функции page_title

Начнём с написания функции, которая принимает URL одной страницы, отправляет запрос по этому адресу и возвращает текст элемента <title> (см. Листинг 17-1).

extern crate trpl; // required for mdbook test

fn main() {
    // TODO: we'll add this next!
}

use trpl::Html;

async fn page_title(url: &str) -> Option<String> {
    let response = trpl::get(url).await;
    let response_text = response.text().await;
    Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html())
}

Сначала мы определяем функцию с именем page_title и помечаем её ключевым словом async. Затем используем функцию trpl::get, чтобы получить страницу по переданному URL, и добавляем ключевое слово await, чтобы дождаться ответа. Чтобы получить текст response, мы вызываем его метод text и снова используем await. Оба этих шага являются асинхронными. При вызове get нам приходится ждать, пока сервер отправит первую часть ответа, содержащую HTTP-заголовки, cookie и прочие данные, которые могут передаваться отдельно от тела ответа. Особенно если тело ответа очень большое, его получение может занять некоторое время. Поскольку нам нужно дождаться получения всего ответа, метод text также является асинхронным.

Мы должны явно ожидать завершения обоих фьючерсов, поскольку фьючерсы в Rust являются ленивыми: они ничего не делают, пока вы не попросите их об этом с помощью ключевого слова await. (На самом деле Rust выдаст предупреждение компилятора, если вы не используете фьючерс.) Это может напомнить вам обсуждение итераторов в разделе «Обработка последовательности элементов с помощью итераторов» главы 13. Итераторы ничего не делают, пока вы не вызовете их метод next — напрямую либо с помощью циклов for или таких методов, как map, которые используют next внутри себя. Аналогично, фьючерсы ничего не делают, пока вы явно не попросите их об этом. Благодаря такой ленивости Rust может не выполнять асинхронный код до тех пор, пока он действительно не понадобится.

Примечание: Это отличается от поведения, которое мы наблюдали при использовании thread::spawn в разделе «Создание нового потока с помощью spawn» главы 16: замыкание, переданное другому потоку, начинало выполняться немедленно. Это также отличается от подхода к асинхронности во многих других языках. Но такое поведение важно для того, чтобы Rust мог обеспечивать свои гарантии производительности, как и в случае с итераторами.

Получив response_text, мы можем разобрать его и создать экземпляр типа Html с помощью Html::parse. Вместо обычной строки теперь у нас есть тип данных, позволяющий работать с HTML как с более сложной структурой данных. В частности, мы можем использовать метод select_first, чтобы найти первое вхождение заданного CSS-селектора. Передав строку "title", мы получим первый элемент <title> в документе, если он существует. Поскольку подходящего элемента может не быть, select_first возвращает Option<ElementRef>. Наконец, мы используем метод Option::map, который позволяет обработать значение внутри Option, если оно присутствует, и ничего не делать, если его нет. (Здесь также можно было бы использовать выражение match, но map считается более идиоматичным.) В теле функции, переданной в map, мы вызываем у title метод inner_html, чтобы получить его содержимое в виде String. В результате мы получаем Option<String>.

Обратите внимание: ключевое слово await в Rust располагается после выражения, завершения которого мы ожидаем, а не перед ним. Иными словами, это постфиксное ключевое слово. Возможно, это отличается от привычного вам синтаксиса async в других языках, но в Rust такое расположение позволяет удобнее выстраивать цепочки вызовов методов. Поэтому мы могли бы изменить тело page_title, объединив вызовы trpl::get и text в цепочку и расположив await между ними, как показано в Листинге 17-2.

extern crate trpl; // required for mdbook test

use trpl::Html;

fn main() {
    // TODO: we'll add this next!
}

async fn page_title(url: &str) -> Option<String> {
    let response_text = trpl::get(url).await.text().await;
    Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html())
}

Итак, мы успешно написали нашу первую асинхронную функцию! Прежде чем добавить в main код для её вызова, давайте подробнее обсудим то, что мы написали, и разберёмся, что это означает.

Когда Rust встречает блок, помеченный ключевым словом async, он компилирует его в уникальный анонимный тип данных, реализующий трейт Future. Когда Rust встречает функцию, помеченную async, он компилирует её в обычную, не асинхронную функцию, тело которой представляет собой асинхронный блок. Возвращаемый тип асинхронной функции — это тип анонимного типа данных, который компилятор создаёт для этого асинхронного блока.

Таким образом, запись async fn эквивалентна записи функции, возвращающей фьючерс с указанным типом результата. Для компилятора определение функции async fn page_title из Листинга 17-1 примерно эквивалентно следующей обычной функции:

#![allow(unused)]
fn main() {
extern crate trpl; // required for mdbook test
use std::future::Future;
use trpl::Html;

fn page_title(url: &str) -> impl Future<Output = Option<String>> {
    async move {
        let text = trpl::get(url).await.text().await;
        Html::parse(&text)
            .select_first("title")
            .map(|title| title.inner_html())
    }
}
}

Разберём каждую часть преобразованной версии:

  • Здесь используется синтаксис impl Trait, который мы обсуждали в главе 10, в разделе «Трейты в качестве параметров».
  • Возвращаемое значение реализует трейт Future с ассоциированным типом Output. Обратите внимание, что тип Output — это Option<String>, то есть он совпадает с исходным возвращаемым типом версии page_title, объявленной с помощью async fn.
  • Весь код из тела исходной функции обёрнут в блок async move. Помните, что блоки являются выражениями. Именно этот блок целиком представляет собой выражение, возвращаемое функцией.
  • Этот асинхронный блок создаёт значение типа Option<String>, как было описано выше. Этот тип значения совпадает с типом Output в возвращаемом типе функции. Это работает так же, как и с другими блоками, которые вы уже видели.
  • Новое тело функции является блоком async move из-за того, как в нём используется параметр url. (Позже в этой главе мы гораздо подробнее обсудим различия между async и async move.)

Теперь мы можем вызвать page_title из main.

Выполнение асинхронной функции с помощью среды выполнения

Для начала получим заголовок одной страницы, как показано в Листинге 17-3. К сожалению, пока этот код не компилируется.

extern crate trpl; // required for mdbook test

use trpl::Html;

async fn main() {
    let args: Vec<String> = std::env::args().collect();
    let url = &args[1];
    match page_title(url).await {
        Some(title) => println!("The title for {url} was {title}"),
        None => println!("{url} had no title"),
    }
}

async fn page_title(url: &str) -> Option<String> {
    let response_text = trpl::get(url).await.text().await;
    Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html())
}

Здесь мы следуем тому же шаблону, который использовали для получения аргументов командной строки в разделе «Приём аргументов командной строки» главы 12. Затем передаём аргумент URL функции page_title и ожидаем результат. Поскольку значение, создаваемое фьючерсом, имеет тип Option<String>, мы используем выражение match, чтобы вывести разные сообщения в зависимости от того, есть ли на странице элемент <title>.

Единственное место, где можно использовать ключевое слово await, — асинхронные функции или блоки, а Rust не позволяет пометить специальную функцию main как async.

error[E0752]: `main` function is not allowed to be `async`
 --> src/main.rs:6:1
  |
6 | async fn main() {
  | ^^^^^^^^^^^^^^^ `main` function is not allowed to be `async`

Причина, по которой main нельзя пометить как async, заключается в том, что асинхронному коду нужна среда выполнения (runtime): крейт Rust, который управляет деталями выполнения асинхронного кода. Функция main программы может инициализировать среду выполнения, но сама по себе такой средой не является. (Чуть позже мы подробнее разберём, почему это так.) В каждой программе на Rust, выполняющей асинхронный код, должно быть хотя бы одно место, в котором настраивается среда выполнения фьючерсов.

В большинстве языков, поддерживающих асинхронность, среда выполнения встроена в язык, но Rust не предоставляет её. Вместо этого существует множество различных асинхронных сред выполнения, каждая из которых предлагает компромиссы, подходящие для определённых сценариев использования. Например, высокопроизводительный веб-сервер с большим количеством ядер процессора и большим объёмом оперативной памяти имеет совершенно иные потребности, чем микроконтроллер с одним ядром, небольшим объёмом памяти и отсутствием возможности выделять память в куче. Крейт, предоставляющий такую среду выполнения, часто также содержит асинхронные версии распространённых возможностей, например файлового и сетевого ввода-вывода.

Здесь и далее в этой главе мы будем использовать функцию block_on из крейта trpl. Она принимает фьючерс в качестве аргумента и блокирует текущий поток до тех пор, пока этот фьючерс не выполнится полностью. Внутри вызов block_on настраивает среду выполнения с помощью крейта tokio, которая используется для выполнения переданного фьючерса (поведение block_on из trpl аналогично функциям block_on в других крейтах сред выполнения). Когда фьючерс завершается, block_on возвращает созданное им значение.

Мы могли бы напрямую передать фьючерс, возвращаемый page_title, в block_on, а после его завершения использовать match для обработки полученного Option<String>, как мы пытались сделать в Листинге 17-3. Однако в большинстве примеров этой главы (и в большинстве реального асинхронного кода) нам потребуется выполнять не один вызов асинхронной функции. Поэтому вместо этого мы передадим асинхронный блок и явно дождёмся результата вызова page_title, как показано в Листинге 17-4.

extern crate trpl; // required for mdbook test

use trpl::Html;

fn main() {
    let args: Vec<String> = std::env::args().collect();

    trpl::block_on(async {
        let url = &args[1];
        match page_title(url).await {
            Some(title) => println!("The title for {url} was {title}"),
            None => println!("{url} had no title"),
        }
    })
}

async fn page_title(url: &str) -> Option<String> {
    let response_text = trpl::get(url).await.text().await;
    Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html())
}

Наконец-то у нас есть работающий асинхронный код! Но прежде чем добавить код, который будет запускать запросы к двум сайтам одновременно, ненадолго вернёмся к тому, как работают фьючерсы.

Каждая точка ожидания (await point), то есть каждое место, в котором код использует ключевое слово await, представляет собой точку передачи управления обратно среде выполнения. Чтобы это работало, Rust должен отслеживать состояние асинхронного блока, чтобы среда выполнения могла запустить какую-нибудь другую работу, а затем вернуться к первому блоку, когда тот будет готов продолжить выполнение. Это невидимая машина состояний, как если бы вы написали перечисление вроде следующего, чтобы сохранять текущее состояние в каждой точке ожидания:

#![allow(unused)]
fn main() {
extern crate trpl; // required for mdbook test

enum PageTitleFuture<'a> {
    Initial { url: &'a str },
    GetAwaitPoint { url: &'a str },
    TextAwaitPoint { response: trpl::Response },
}
}

Однако вручную писать код переходов между состояниями было бы утомительно и чревато ошибками, особенно если впоследствии потребуется добавить в программу новые возможности и состояния. К счастью, компилятор Rust автоматически создаёт структуры данных машины состояний и управляет ими для асинхронного кода. Обычные правила заимствования и владения для структур данных по-прежнему действуют. К счастью, компилятор также проверяет их за нас и выдаёт полезные сообщения об ошибках. Несколько таких случаев мы рассмотрим позднее в этой главе.

В конечном счёте кто-то должен выполнять эту машину состояний, и эту задачу берёт на себя среда выполнения. (Именно поэтому при изучении сред выполнения вы можете встретить термин исполнитель (executor): это часть среды выполнения, отвечающая за выполнение асинхронного кода.)

Теперь вы можете понять, почему компилятор не позволил нам сделать саму main асинхронной функцией в Листинге 17-3. Если бы main была асинхронной функцией, что-то другое должно было бы управлять машиной состояний фьючерса, возвращаемого main, но ведь main — это точка входа программы! Вместо этого мы вызвали в main функцию trpl::block_on, чтобы настроить среду выполнения и выполнять фьючерс, возвращаемый асинхронным блоком, до его завершения.

Примечание: Некоторые среды выполнения предоставляют макросы, позволяющие писать асинхронную функцию main. Эти макросы преобразуют async fn main() { ... } в обычную fn main, которая делает то же самое, что мы вручную реализовали в Листинге 17-4: вызывает функцию, выполняющую фьючерс до завершения, подобно trpl::block_on.

Теперь давайте объединим эти элементы и посмотрим, как писать конкурентный код.

Конкурентная гонка между двумя URL-адресами

В Листинге 17-5 мы вызываем page_title с двумя разными URL-адресами, переданными из командной строки, и устраиваем гонку фьючерсов, выбирая тот, который завершится первым.

extern crate trpl; // required for mdbook test

use trpl::{Either, Html};

fn main() {
    let args: Vec<String> = std::env::args().collect();

    trpl::block_on(async {
        let title_fut_1 = page_title(&args[1]);
        let title_fut_2 = page_title(&args[2]);

        let (url, maybe_title) =
            match trpl::select(title_fut_1, title_fut_2).await {
                Either::Left(left) => left,
                Either::Right(right) => right,
            };

        println!("{url} returned first");
        match maybe_title {
            Some(title) => println!("Its page title was: '{title}'"),
            None => println!("It had no title."),
        }
    })
}

async fn page_title(url: &str) -> (&str, Option<String>) {
    let response_text = trpl::get(url).await.text().await;
    let title = Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html());
    (url, title)
}

Сначала мы вызываем page_title для каждого URL-адреса, переданного пользователем. Полученные фьючерсы сохраняем в переменные title_fut_1 и title_fut_2. Помните, что пока они ничего не делают: фьючерсы ленивы, и мы ещё не ожидали их завершения. Затем передаём фьючерсы в trpl::select, которая возвращает значение, указывающее, какой из переданных фьючерсов завершился первым.

Примечание: Внутри trpl::select построена на более общей функции select, определённой в крейте futures. Функция select из крейта futures умеет гораздо больше, чем trpl::select, но она также обладает дополнительной сложностью, которую пока можно не рассматривать.

Любой из фьючерсов может совершенно законно «победить», поэтому возвращать Result здесь не имеет смысла. Вместо этого trpl::select возвращает тип, который мы ещё не встречали, — trpl::Either. Тип Either отчасти похож на Result, поскольку у него есть два варианта. Однако, в отличие от Result, в Either нет встроенного понятия успеха или ошибки. Вместо этого варианты Left и Right обозначают «одно или другое»:

#![allow(unused)]
fn main() {
enum Either<A, B> {
    Left(A),
    Right(B),
}
}

Функция select возвращает Left с результатом первого фьючерса, если побеждает первый аргумент, и Right с результатом второго фьючерса, если побеждает второй. Это соответствует порядку аргументов при вызове функции: первый аргумент находится слева от второго.

Мы также изменим page_title, чтобы она возвращала URL-адрес, который ей передали. Благодаря этому, если страница, загрузившаяся первой, не содержит элемента <title>, который удалось бы извлечь, мы всё равно сможем вывести осмысленное сообщение. Имея эту информацию, мы завершаем пример, изменяя вывод println!, чтобы он показывал, какой URL завершился первым, а также какой элемент <title>, если он есть, найден на соответствующей веб-странице.

Теперь вы создали небольшой работающий веб-скрейпер! Выберите несколько URL-адресов и запустите утилиту командной строки. Возможно, вы обнаружите, что некоторые сайты стабильно работают быстрее других, а в других случаях самый быстрый сайт меняется от запуска к запуску. Но, что важнее, вы изучили основы работы с фьючерсами, поэтому теперь мы можем подробнее рассмотреть возможности асинхронного программирования.
